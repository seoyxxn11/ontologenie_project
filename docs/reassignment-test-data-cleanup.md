# 재배정 테스트 기록 정리

2026-11-17 사용자 요청으로 확인한 테스트 계획 6건 전체와 연결 대화를 정리한다. Jira 이슈는 만들지 않는다.

## 적용 대상

| 계획 ID | 연결 대화 ID | 생성 실행 ID | 항목 수 |
| --- | --- | --- | --- |
| 1 | 48 | 758 | 2 |
| 2 | 96 | 1615 | 2 |
| 3 | 102 | 1665 | 1 |
| 4 | 103 | 1697 | 2 |
| 5 | 133 | 1987 | 2 |
| 6 | 151 | 2172 | 2 |

계획 1·2·4·5·6은 같은 작업지시의 공정 20·30을 같은 설비로 옮기는 계획이다. 계획 3은 같은 작업지시의 전체 공정을 대상으로 한다. 사용자는 이 차이를 확인한 뒤 6건 전체 삭제를 선택했다.

읽기 전용 확인 당시 대화 48·102·103·133·151은 이미 숨겨져 있었고 대화 96만 목록에 남아 있었다. 이미 숨긴 시각은 유지한다.

## 동작과 보호 조건

`V28__remove_approved_reassignment_test_plans.sql`이 계획 헤더 6건과 FK로 연결된 항목 11건을 삭제하고, 연결 대화의 `deleted_at`을 채운다. 메시지, `action_execution`, `entity_change`, 원천 객체와 실제 MES 배정은 보존한다. DB 스키마와 API 계약은 바뀌지 않으므로 ERD·OpenAPI 변경은 없다.

계획 ID만으로 삭제하지 않는다. 승인 당시의 정확한 생성 시각, 대화·실행 ID, 작성 계정, 기존 설비와 상태가 모두 일치하는 계획만 선택한다. 빈 DB나 다른 환경에서 이 조건과 일치하지 않으면 변경하지 않는다. 이미 삭제된 계획도 건너뛰며, 이 경우 대화만 따로 숨기지 않는다.

일치한 계획의 작업지시·공정·대체 설비가 달라졌거나 대화에 새 메시지, 실행 중인 답변, 다른 계획이 있으면 예외로 전체 마이그레이션을 원복한다. 대상 계획·대화·항목·메시지 행을 잠근 뒤 확인한다. 새 메시지와 새 계획은 대화 FK를 확인할 때 대화 잠금과 경합한다.

이 작업은 이번에 확인한 데이터만 정리한다. 이후 새로 저장하는 계획의 생성·중복 판단 규칙은 바꾸지 않는다.

## 배포와 복구

운영 DB에 수동 DELETE를 실행하지 않는다. MR 검토·병합 후 backend 배포에서 Flyway가 단일 트랜잭션으로 적용한다. MR 생성만으로 운영 데이터가 삭제되지는 않는다. 병합·배포는 사람이 수행한다.

삭제는 데이터 복구가 필요한 작업이므로 병합 전에 운영자가 [기존 DB 백업 절차](../infra/README.md#db-백업--복구)에 따라 복구 가능한 백업을 확인한다. 이 MR 작업에서는 운영 백업을 새로 만들거나 운영 데이터를 변경하지 않는다. 적용 후에는 다음을 확인한다.

- 대상 계획 6건과 항목 11건이 없어졌는지
- 대화 6개가 숨겨졌고 기존 `deleted_at`이 유지됐는지
- 메시지·실행·감사 기록 및 대상 밖의 계획·대화가 유지됐는지

애플리케이션 버전을 되돌려도 삭제된 계획은 복원되지 않는다. 복구가 필요하면 백업을 별도 복구 DB에 복원해 승인 대상의 계획·항목만 확인하여 원래 ID로 되돌리는 별도 데이터 복구가 필요하다. 이미 존재하는 실행·메시지는 다시 넣지 않으며, 원래 보이던 대화 96만 숨김을 해제한다. 전체 운영 DB를 과거 백업으로 덮어쓰면 이후 업무 기록이 손실될 수 있으므로 그렇게 복구하지 않는다.

## 검증 범위

`ReassignmentTestDataCleanupMigrationTests`는 운영 데이터 원문 없이 만든 합성 데이터로 실제 PostgreSQL에서 SQL을 실행한다. 승인 대상 삭제, 대상 밖 데이터·원천 객체·감사 기록·메시지 보존, 기존 숨김 시각 유지, 재실행, 다른 생성 시각의 동일 ID 보존, 이미 없는 계획의 대화 보존, 항목 변경·새 메시지·실행 중인 답변·다른 계획 연결 시 전체 원복을 확인한다. `DatabaseMigrationTests`는 빈 DB의 전체 Flyway 이력에 V28이 포함되는지 확인한다.
