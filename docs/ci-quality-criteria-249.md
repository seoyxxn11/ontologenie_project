### 현재 MR 검사 명령

다음은 **이미 구성된 명령**이다. 이번 작업으로 새 필수 정책을 설정한 것이 아니다. 운영 Jenkins가 같은 설정을 사용하고 실제로 실행했는지는 별도 증거가 필요하다.

| 변경 범위                                | 검사·환경                                                                                                                                   | 현재 결과 판정과 제한                                                                                                  |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `backend/`                               | Java 21, `./gradlew --no-daemon spotlessCheck build`. Testcontainers용 Docker 필요                                                          | 명령 실패 시 MR 검사 실패. JUnit XML 수집은 `allowEmptyResults: true`이므로 보고서 수집 자체가 테스트 실행 증거는 아님 |
| `frontend/`                              | Node `24.18.0-alpine` 컨테이너에서 `npm ci --no-audit --no-fund`, `npm run lint`, `npx vitest run`, `npm run build`                         | ESLint·테스트·TypeScript/Vite 빌드 실패 시 MR 검사 실패. `npm run format:check`는 현재 MR 명령에 없음                  |
| `ai/`                                    | Python `3.11-slim` 컨테이너에서 `pip install -q -r requirements-dev.txt`, `ruff check .`, `pytest -q --junitxml=test-results/pytest.xml`    | 설치·Ruff·pytest 실패 시 MR 검사 실패. 실제 LLM 비용·성능·운영 연동의 통과 증거와 구분                                 |
| `infra/` 또는 `Jenkinsfile`              | `bash -n`으로 `sync-config.sh`, 존재하면 `sync-sonarqube.sh`, `pg-backup.sh` 검사. `python:3.11-slim`에서 `infra/deploy/test_*.py` unittest | Linux bash 환경을 사용. 해당 unittest 컨테이너는 네트워크 없음. 실제 서버 배포·복구 성공을 증명하지 않음               |

Jenkinsfile 자체는 develop에서 읽는다고 파일에 명시되어 있다. 작업 브랜치의 Jenkinsfile 변경이 해당 MR 검사에서 그대로 실행됐다고 간주하지 않는다. 서비스 폴더 밖 공통 변경이 다른 서비스에도 영향을 주면 폴더 기반 선택만으로 충분한지 검토해야 한다.

### SonarQube 분석 범위

| 서비스 | 프로젝트 키       | 소스·테스트                                                               | Coverage 입력                                                                               |
| ------ | ----------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 프론트 | `axcore-frontend` | `src`, 테스트 `src/**/*.test.ts`·`src/**/*.test.tsx`를 소스 분석에서 제외 | `npm run test:coverage` → `coverage/lcov.info`                                              |
| 백엔드 | `axcore-backend`  | `src/main`·`src/test`, Java 21 및 컴파일 결과                             | `./gradlew --no-daemon jacocoTestReport` → `build/reports/jacoco/test/jacocoTestReport.xml` |
| AI     | `axcore-ai`       | `app,main.py`·`tests`, Python 3.11                                        | `pytest -q --cov --cov-report=xml` → `coverage/coverage.xml`                                |

근거는 각 서비스의 `sonar-project.properties`, 백엔드 `build.gradle`, 프론트 `package.json`·`vite.config.ts`, AI `.coveragerc`다. 인프라·문서용 별도 SonarQube 프로젝트는 이 설정에 없다.

- 배포 Job에서는 `ENABLE_SONARQUBE=true`, SonarQube 준비 완료, 해당 서비스 배포 대상 또는 `RUN_SONARQUBE` 등의 조건에 따라 develop 분석을 수행한다.
- `axcore-mr-check`는 Webhook 이벤트가 없는 수동 실행에서 `RUN_SONARQUBE`를 켜고 `origin/develop`을 검사하는 경우만 SonarQube 분석을 수행한다. 일반 MR 커밋의 분석 결과로 해석하지 않는다.
- 해당 분석의 보고서는 존재·비어 있지 않음을 검사한다. 보고서 생성·분석 단계 실패는 Jenkins 실행을 실패로 표시할 수 있다.
- **Quality Gate 미통과 또는 Gate 상태 조회 실패**는 별개다. 조건에 맞는 develop push 실행에서 제출한 분석의 Gate를 조회하고 미통과 링크를 알리지만, Gate 미통과 자체로 배포 결과를 실패로 바꾸지 않는다.
- 실제 서버의 Gate 조건·프로젝트별 적용 Gate·New Code 기준·제외 설정·현재 수치는 미확인이다. 기본 Gate나 특정 Coverage 임계값을 사용한다고 추정하지 않는다.

- Linux 전용 셸 회귀 검사: Windows 결과에 포함되지 않는다. Linux CI 결과로 추가 확인해야 한다.
- Jenkins Webhook/실제 MR 커밋 상태, GitLab 보호·승인 설정, SonarQube Gate 현재 설정과 실제 실패 차단: 서버·서비스 설정을 변경하거나 실패를 유발하지 않았다. 후속 읽기 전용 확인 및 팀 합의 필요.
- Notion 개발 가이드 사본은 연결 도구에서 404로 조회하지 못했다. 저장소 가이드가 원본이며, Notion 사본과 동기화했다고 보고하지 않는다. 합의 후 접근 가능한 담당자가 사본을 갱신하고 차이를 확인해야 한다.

## 후속 확인과 완료 판단

1. 공동 담당 및 위 결정 표의 정책을 팀에서 확정하고 승인 근거를 기록한다.
2. 필수 범위가 확정되면 [개발 가이드](development-guide.md) 12·13절 및 [테스트 규칙](../.ai/rules/testing.md)의 미결정 항목을 실제 합의로 갱신하고 Notion 사본을 맞춘다.
3. CI·Gate 설정 변경이 필요하면 대상·영향을 구분해 별도 승인된 작업으로 진행한다. 이번 249 문서 변경으로 설정 구축·배포를 수행하지 않는다.
4. 담당자 외 팀원 리뷰와 MR 병합 후 문서·링크·설정과의 일치 여부를 확인한다. 미확정 공동 담당·정책이 남아 있으면 전체 완료로 표시하지 않는다.
