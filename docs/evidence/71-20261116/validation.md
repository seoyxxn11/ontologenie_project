# S15P31C106-71: 주요 API 응답 시간 측정

## 준비 확인

2026-11-16 KST에 기존 `axcore` SSH 프로필로 서버 호스트 이름 조회에 성공했다. backend·AI·PostgreSQL·Grafana는 healthy이고 nginx·Alloy·Loki도 실행 중이다. backend 내부 health는 HTTP 200이었다. 호스트 13100의 Loki `/ready` 접근은 연결되지 않았으므로 컨테이너 실행만으로 Loki 수집 준비가 완료됐다고 단정하지 않는다.

읽기 전용 DB 조회로 연결 원천 2개, 리소스 29개, 객체 유형 25개, 객체 3,397개를 확인했다. 측정용 객체 3·731, 완료 분석 25(`SUCCEEDED`), 기존 대화 146(메시지 2개)이 존재한다. AI 후보는 132개, 정합성 문제는 6개다. 실제 API의 권한과 반환 데이터는 로그인 후 사전 요청으로 다시 확인한다.

준비 확인 요약은 [readiness.json](readiness.json)에 기록했다. 서버 접근·데이터 존재 확인 자료이며 성능 표본으로 사용하지 않는다.

실제 `.env`·개인 키·인증서·자격 증명 파일은 읽지 않았다. 서버 파일·배포 설정·업무 데이터는 변경하지 않았다. 작업 브랜치는 최신 `origin/develop`(`b1a04f1a`)에서 만든 `feature/71-api-performance`다.

Commit 준비 시 원격을 다시 fetch해 55번 병합이 추가된 최신 `origin/develop`(`e9a3e080`)을 fast-forward로 반영했다. 71번 작업 파일과 겹치는 변경이 없어 충돌은 없었다. 측정기·테스트 코드는 그대로이며 같은 코드 상태에서 실행한 검증 결과를 사용했다.

## 요구사항 및 도구 선택

- [Jira 71](https://ssafy.atlassian.net/browse/S15P31C106-71)은 API 5~10개에 대해 단일·동시 5~10개 요청의 평균·p95 측정을 요구한다.
- [Jira 24](https://ssafy.atlassian.net/browse/S15P31C106-24) 본문에는 응답 시간 수치 목표가 없다.
- [기획서 v1.0 초안 13절](https://app.notion.com/p/40dbdf14d2d88190afe3fb8c27bc4a5a#a407842b9c9c4e16914b5c805e2891d9)은 응답에 대해 “긴 분석은 비동기(202). Agent는 스트리밍 없이 반복 조회. 수치 목표 미정”이라고 명시한다. 연결된 Notion Primary 계정은 팀 페이지를 읽지 못해 기존 브라우저 세션으로 문서를 확인했다. 초안의 값이며 확정된 수치 목표로 취급하지 않는다.
- 현재 서버 nginx 로그 형식에는 `$request_time`·`$upstream_response_time`이 없다. backend HTTP 지표에는 count·sum 등이 있으나 histogram bucket·quantile이 없다. 이 자료만으로 API별 p95를 계산할 수 없다.
- 서버 로깅·배포를 변경하는 대신 Python 표준 라이브러리 측정기를 추가했다. k6 등 의존성은 추가하지 않았다.

## 고정 측정 범위

| 대상 | GET 경로 | 시연 데이터 |
| --- | --- | --- |
| 객체 검색 | `/api/v1/objects?q=P103&page=0&size=20` | P103 검색어, 첫 20개 결과 |
| 객체 상세 | `/api/v1/objects/3` | 설비 객체 3 |
| 객체 관계 | `/api/v1/objects/3/links?page=0&size=20` | 기존 활성 관계 |
| AI 제안 목록 | `/api/v1/proposals?origin=AI&page=0&size=20` | 기존 후보 |
| 정합성 문제 목록 | `/api/v1/issues?page=0&size=20` | 기존 문제 |
| 분석 상태 조회 | `/api/v1/analyses/25` | 완료 분석 |
| Agent 메시지 조회 | `/api/v1/agent/conversations/146/messages?page=0&size=20` | 기존 완료 시간 계산 대화 |

각 API는 사전 확인·워밍업 1회 후 단일 20회, 동시 5개씩 20회(4묶음)를 실행한다. 사전 확인 7회와 본 측정 280회를 구분한다. 실패한 요청이 있으면 현재 전송한 묶음까지만 마치고 다음 요청을 중단한다. 본 측정 약 5분 이후에는 다음 묶음을 시작하지 않으며 이미 진행 중인 요청에는 소켓 timeout 15초가 적용된다.

이는 계정 하나로 보내는 동시 요청 측정이며 서로 다른 사용자 5명의 세션·역할·사용 흐름을 재현하는 것은 아니다. 새 Agent 질문·분석·LLM·데이터 변경 Action은 실행하지 않는다. Agent 답변 생성 및 완료 시간 계산 작업 자체의 동시 성능은 이 범위에 포함되지 않는다. 55번의 3개 표본으로 새로운 동시 p95를 대신하지 않는다.

## 시간·통계 정의

- 측정 위치: 사용자 PC → `https://ontologenie.com` nginx → backend. 요청마다 새 연결을 열므로 DNS·TCP·TLS·본문 수신 시간을 포함한다. 브라우저의 연결 재사용·화면 렌더링 시간은 아니다.
- 사전 확인은 모든 경로에서 HTTP 200·정상 JSON 형식·비어 있지 않은 시연 데이터가 나오는지 검사한다. 사전 확인 실패 시 부하 측정을 시작하지 않는다.
- 평균·p95는 정상 응답만 계산하되 실패 건수·총 시도·완료 여부를 별도로 표시한다. 빠른 오류 응답을 정상 응답 시간에 섞지 않는다.
- p95는 `ceil(n × 0.95)` 순위 값(nearest-rank)이다. 20개 중 19번째 값이며 모집단 p95를 높은 신뢰도로 추정하는 대규모 표본은 아니다.
- 목표가 확정되지 않았으므로 `nfr_target_ms=null`, `nfr_result=UNDEFINED_TARGET`으로 기록한다. 임의로 달성·미달을 만들지 않는다.
- 비밀번호·세션·CSRF 토큰·로그인 ID·업무 응답 본문은 결과 파일에 저장하지 않는다. 쿠키는 인증한 새 세션의 메모리에만 두며 측정 후 그 세션을 로그아웃한다. redirect는 허용하지 않는다.

## 실행

```powershell
python infra/scripts/measure_api_performance.py --login-window --output docs/evidence/71-20261116/results.json
```

로컬 로그인 창에서 시연 관리자 계정으로 직접 인증한다. 비밀번호를 채팅·명령 인자·파일로 전달하지 않는다. 기존 결과 파일이 있으면 다른 이름을 사용하여 원시 기록을 보존한다. 로그인은 새 세션을 만들며 기존 브라우저 세션을 추출하거나 재사용하지 않는다.

## 실제 측정 결과

사용자가 로컬 로그인 창에서 직접 인증하고 측정을 시작했다. 측정기 기록 기준 KST **20:42:13~20:43:14**에 사전 확인 7건과 본 측정 **280건(7개 API × 2조건 × 20회)**을 마쳤다. 전부 HTTP 200·정상 응답 검사를 통과했고 실패는 **0건**이었다. 측정 후 새로 만든 세션의 로그아웃도 성공했다.

단위는 **ms**, 각 칸의 표본 수는 20개다. 사전 확인 7건은 아래 통계에 포함하지 않았다.

| API | 단일 평균 | 단일 p95 | 동시 5개 평균 | 동시 5개 p95 | NFR 비교 |
| --- | ---: | ---: | ---: | ---: | --- |
| 객체 검색 | 1284.3 | 1567.8 | 3784.0 | 4121.8 | 목표 미정 |
| 객체 상세 | 61.2 | 84.6 | 72.6 | 84.2 | 목표 미정 |
| 객체 관계 | 111.8 | 149.4 | 252.5 | 612.2 | 목표 미정 |
| AI 제안 목록 | 97.8 | 112.9 | 126.1 | 153.6 | 목표 미정 |
| 정합성 문제 목록 | 67.5 | 81.5 | 81.9 | 99.5 | 목표 미정 |
| 분석 상태 조회 | 54.1 | 70.2 | 67.8 | 80.0 | 목표 미정 |
| Agent 메시지 조회 | 75.3 | 90.6 | 96.6 | 116.9 | 목표 미정 |

원시 기록은 [results.json](results.json), 별도 계산 코드로 대조한 요약은 [summary.json](summary.json)이다. 14조건 모두 20개 표본·성공 상태·중복 없는 표본 번호·평균·nearest-rank p95가 일치했다. 시작 시각과 소요 시간으로 구성한 요청 구간에서도 단일 조건 최대 1개, 동시 조건 최대 **5개**가 실제로 겹쳤다.

### 우선 조사 후보

**객체 검색**은 단일 p95 약 1.57초에서 동시 5개 p95 약 **4.12초**로 늘어 이번 7개 API 중 가장 길었다. 평균은 약 1.28초에서 3.78초로 늘었다. 동일한 검색어·페이지·계정 조건을 기준으로 검색 쿼리, DB 실행 계획·인덱스, 권한 범위 계산, 세션·커넥션 풀 대기 시간을 분리해 조사할 근거가 된다. 이 세부 구간은 아직 계측하지 않았으므로 특정 SQL이나 DB 잠금을 원인으로 단정하지 않는다.

객체 관계 조회도 동시 조건 p95가 약 149ms에서 612ms로 늘어 다음 조사 후보로 남긴다. 수치 목표가 정해지지 않았으므로 두 API를 NFR 미달로 판정하거나 자동으로 개선 이슈를 만들지는 않았다. 이번 작업에서 서비스 코드를 변경하거나 운영 DB에 EXPLAIN ANALYZE·인덱스 변경 등을 실행하지 않았다.

### 서버 영향 및 범위 확인

[server-after.json](server-after.json)의 측정 시간대 nginx 라우팅 집계는 GET 200 **291건**, POST 204 **1건**, 504 **0건**이었다. 전체 backend 라우팅 기록 집계여서 본 측정 외의 요청도 포함한다. 사용자 PC에서 기록한 사전 확인 7건·본 측정 280건과 nginx 전체 291건을 같은 표본 수로 취급하지 않는다. 요청별 URI·인증 정보·본문을 수집하지 않았다.

backend·AI·PostgreSQL·Grafana는 종료 후에도 healthy였고 nginx는 running이었다. 준비 확인 때와 컨테이너 시작 시각이 같고 OOMKilled는 모두 false였다. 업무 데이터 건수는 객체 3,397개, 분석 5건, Agent 메시지 576건, 감사 실행 2,107건, 후보 132건, 문제 6건으로 준비 확인 때와 같았다. 이는 관측한 건수 확인이며 모든 행의 불변성을 검증한 체크섬은 아니다. 측정 경로는 고정 GET만 사용했고 새 분석·Agent 질문·LLM·데이터 변경 Action을 요청하지 않았다.
