### P01: 사용자 목표에 해당하는 특이사항을 실제로 발견

조회 순서는 수주 → 수주 상세 → 작업지시 → 두 작업지시의 현재 공정 → 중단 공정의 설비 비가동 기록이었다. 목표 유형 찾기 5회를 모두 성공했다. 특히 4번째는 [730, 731]을 묶어 현재 공정 전체를 읽었고, 5번째는 중단 공정 [579, 580]에서 `작업지시 공정 배정 → 설비 → 설비 비가동 기록`을 따라갔다.

최종 답변은 JB2610-0141의 20·30공정 중단, 각 잔량 3,200개, P103의 DT-0460, 슬라이드 유압 누유, 10/30 03:10 시작 및 종료 기록 없음을 담았다. 따라서 단순히 상위 “생산중” 상태를 반복한 답변은 아니다.

설비 객체의 현재 상태 속성 “정비중”을 직접 조회한 것은 아니다. 중단 공정과 연결된 같은 설비의 비가동 기록 중 작업지시가 JB2610-0141이고 종료 기록이 없는 사건을 근거로 원인을 설명했다. GMS 원문에서 이를 확인했다. 조회된 설비 비가동 10건 중 과거 종료 기록 9건도 읽었으므로, 현행 도구가 필요한 사건만 정확히 좁힌 효율적인 조회였다고까지 평가하지 않는다.

이 실행의 4·5번째 FIND는 기존 3회 한도에서는 거절되었을 것이다. 다만 3회 한도에서도 다른 관계 도구로 같은 근거에 도달할 수 있으므로 “3회로는 원인 조회가 절대 불가능”이라는 뜻은 아니다.

### P02·P03: 여유가 생겨도 탐색 대상과 종료 판단은 모델에 남는다

P02는 수주 전체를 찾은 뒤 상태 조건을 붙여 수주를 다시 찾았다. 수주 상세·작업지시를 찾은 후, 현재 공정도 두 작업지시를 묶지 않고 하나씩 찾았다. 5번째 호출을 JB2610-0138에 쓰고, 실제 중단 작업인 JB2610-0141의 6번째 호출에서 한도에 걸렸다. 모델은 미확인 사실은 밝혔지만 중요한 중단을 답하지 못했다. “모르겠다”를 성공으로 세지 않았다.

P03도 작업지시별 공정을 각각 찾고 출하 실적에 한 번을 써 FIND 5회를 사용했다. 현재 중단은 답했으나 원인 조회를 시도하지 않고 끝냈다. 6번째 거절 기록은 없다. 한도 때문에 원인 조회를 포기한 것인지, 충분하다고 판단한 것인지는 이 기록만으로 확정할 수 없다.

남은 공통 문제는 **여러 작업의 현재 상태를 빠짐없이 읽는 탐색 배분**, **중단을 발견한 뒤 원인까지 확인할지 결정하는 종료 판단**이다. 이번에는 한도 외 코드·문구를 바꾸지 않았다.
