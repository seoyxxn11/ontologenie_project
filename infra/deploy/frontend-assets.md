# 프론트 정적 파일 보관 (435)

배포 전에 열어 둔 탭은 이전 버전의 해시가 붙은 JS·CSS를 계속 요청한다. 프론트 컨테이너와 별도로 공개 정적 파일을 보관하고, 메인 nginx가 `/assets/` 요청에 먼저 제공한다. 없는 파일은 현재 frontend로 전달하므로 최초 적용과 수동 롤백도 기존 이미지와 호환된다. HTML은 기존처럼 frontend에서 `no-cache`로 제공한다.

## 배포 순서

1. 설정 반영 전에 Jenkins가 `/home/ubuntu/axcore/frontend-assets`를 준비한다. 심볼릭 링크는 거부한다.
2. 설정 자동 반영이 nginx의 읽기 전용 bind mount와 `/assets/` 경로를 적용한다. 첫 도입은 nginx 서비스 정의가 바뀌므로 nginx가 재생성된다. 새 named volume·네트워크·서비스는 추가하지 않는다.
3. 새 frontend 이미지를 빌드한 뒤 `retain-frontend-assets.sh`가 현재 frontend 컨테이너와 새 이미지의 `/usr/share/nginx/html/assets/` 전체를 임시 디렉터리에 복사한다. 새 이미지는 실행하지 않고 임시 정지 컨테이너에서 읽는다.
4. 네트워크가 차단된 기존 `python:3.11-slim` 컨테이너가 파일을 검증·원자적으로 게시하고 보관 목록을 갱신한다. 같은 이름의 파일 내용이 다르거나 복사·검증에 실패하면 기존 파일을 덮어쓰지 않으며, frontend 태그·컨테이너 교체 전에 배포를 중단한다.
5. 기존 `deployService`가 새 이미지로 교체하고 health를 확인한다. 실패 시 기존 이미지로 롤백한다. 보관소는 별도이므로 교체 전후 파일이 함께 남는다.

보관 대상은 빌드된 `assets/` 전체이며 공유 JS·CSS 및 그 안의 이미지·폰트도 포함한다. HTML·환경 파일·인증서·자격 증명은 복사하지 않는다. `releases.json`은 이미지 ID별 파일 목록과 마지막 보관 시각을 기록한다. 임시 snapshot과 목록은 `/assets/` 밖에 있고 웹 경로로 공개하지 않는다.

## 보관 기간과 정리

- Jenkins 파라미터 `FRONTEND_ASSET_RETENTION_DAYS`의 기본값은 7일이며 1 이상 정수만 허용한다.
- 현재 컨테이너의 파일 목록은 교체 직전 보관 시각으로 다시 갱신한다. 따라서 오랫동안 배포하지 않은 현재 버전을 빌드 날짜 때문에 즉시 삭제하지 않는다. 새 이미지도 같은 시각으로 등록한다.
- 다음 frontend 배포 준비 시 보관 기간이 지난 버전의 목록을 제외한다. 남아 있는 버전이 하나라도 참조하는 파일은 유지한다. 현재·새 이미지의 파일은 항상 유지하며, 이전 목록에 등록된 만료 파일만 지운다. 수동으로 넣은 미등록 파일은 삭제하지 않는다.
- 시간만 지났다고 즉시 정리하는 cron은 추가하지 않는다. 보관소 크기는 배포 빈도·변경량에 따라 늘어나므로 서버 디스크 사용량을 확인한다. 이미지 정리 단계가 이전 Docker 이미지를 삭제해도 보관소 파일에는 영향을 주지 않는다.
- 보관 목록이 깨지거나 경로·심볼릭 링크·파일 내용 충돌이 발견되면 정리·배포를 중단한다. 기존 폴더 전체를 지워 복구하지 말고 오류와 마지막 정상 목록을 확인한다.

보관 기간이 지난 탭은 435의 새 버전 안내에서 새로고침해야 할 수 있다. 적용 이전에 이미 서버에서 사라진 파일은 복원할 수 없다. 이 변경은 HTML 요청의 배포 중 중단까지 없애는 블루그린 배포가 아니다.

## 검증

```sh
python -m unittest discover -s infra/deploy -p 'test_*.py' -v
java -cp '<Gradle 설치 경로>/lib/*' groovy.ui.GroovyMain infra/tests/jenkins-frontend-assets-tests.groovy
```

셸 검사는 Linux bash 환경에서 실행한다. 가짜 Docker 검사는 복사·게시 실패와 정리 경계를 검증하며 실제 nginx·운영 배포를 대신하지 않는다. 실제 nginx 검사는 저장소 루트에서 `python infra/tests/verify_frontend_assets.py`로 로컬 Docker 컨테이너만 사용해 실행한다.

운영 반영 후에는 이전 탭을 유지한 채 frontend를 배포하고, 새로고침 없이 메뉴를 이동했을 때 이전 JS·CSS가 200인지 확인한다. 현재 HTML의 `no-cache`, 해시 파일의 장기 캐시, 없는 파일의 404와 단일 보안 헤더도 확인한다. 실제 서버 적용·Jenkins 배포·TLS·롤백 검증은 별도 수행한다.
