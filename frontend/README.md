# Frontend

온톨로지 플랫폼의 웹 화면입니다. 업무 데이터 탐색(Explorer), AI 업무 도우미(Agent), Action 실행, 감사 이력 조회 화면을 담습니다.

## 기술 스택

| 역할           | 도구                           |
| -------------- | ------------------------------ |
| 화면           | React 19, TypeScript           |
| 개발 서버·빌드 | Vite                           |
| 스타일         | Tailwind CSS                   |
| 화면 이동      | React Router                   |
| 서버 데이터    | TanStack Query                 |
| 가짜 API       | MSW (Mock Service Worker)      |
| 테스트         | Vitest, Testing Library, jsdom |
| 코드 검사·정리 | ESLint, Prettier               |

## 시작하기

Node.js 24와 npm을 사용합니다. 모든 명령은 `frontend` 폴더에서 실행합니다.

```bash
npm install
npm run dev
```

브라우저에서 `http://localhost:5173`을 엽니다. 개발 서버에서는 MSW가 켜져서 백엔드 없이도 `/api/...` 요청에 가짜 응답을 돌려줍니다.

## 명령어

| 명령                   | 하는 일                                   |
| ---------------------- | ----------------------------------------- |
| `npm run dev`          | 개발 서버 실행                            |
| `npm run build`        | 타입 검사 후 배포용 파일을 `dist/`에 생성 |
| `npm run preview`      | 빌드 결과를 로컬에서 확인                 |

변경을 마치면 `npm run lint` → `npm test` → `npm run format:check` 순서로 확인합니다.

## 폴더 구조

> 프론트엔드 초안입니다. 팀 전체 규칙(`.ai/rules/architecture.md`)이 정해지면 그에 맞춰 수정합니다.

```text
src/
├─ main.tsx          앱 시작점 (MSW 켜기, TanStack Query 연결, 화면 그리기)
├─ App.tsx           라우트 (주소 → 화면)
├─ index.css         전역 스타일 (Tailwind)
├─ features/         기능(메뉴)별 폴더
│  ├─ explorer/      업무 데이터 탐색
│  └─ agent/         AI 업무 도우미
├─ components/       두 개 이상의 기능이 같이 쓰는 공통 부품
│  ├─ AppLayout.tsx        모든 화면의 공통 틀 (헤더, 주 메뉴)
│  ├─ PagePlaceholder.tsx  아직 만들지 않은 화면 자리
│  └─ NotFoundPage.tsx     없는 주소 안내
├─ api/              모든 기능이 같이 쓰는 API 공통 코드
│  ├─ client.ts      요청 보내기 (`/api/v1` 주소, 오류 응답 처리)
│  └─ types.ts       공통 응답 형식 (`data`, `meta`, `error`)
├─ mocks/            MSW 가짜 API
│  ├─ handlers.ts    요청별 가짜 응답
│  ├─ browser.ts     개발 서버용 (`npm run dev`)
│  └─ node.ts        테스트용 (`npm test`)
└─ test/
   └─ setup.ts       테스트 공통 준비
```

### 규칙

1. **기능별로 나눕니다.** 메뉴 하나(Explorer, Agent, Action, Audit 등)마다 `features/<기능>/` 폴더를 하나 둡니다. 담당자가 나뉘어도 서로 다른 폴더에서 작업하게 됩니다.
2. **한 기능에서만 쓰는 것은 그 기능 폴더에 둡니다.** 화면 조각, 타입, API 호출 함수가 모두 해당합니다.
3. **두 기능 이상이 같이 쓰게 되면 `components/`로 옮깁니다.** 처음부터 공통으로 만들지 않고, 실제로 두 번째 사용처가 생길 때 옮깁니다.
4. **주소 하나에 대응하는 화면은 `<기능>Page.tsx`로 이름 짓습니다.** 예: `ExplorerPage.tsx`, `AgentPage.tsx`. 라우트 연결은 `App.tsx`에서만 합니다.
5. **테스트 파일은 대상 파일 옆에 둡니다.** `ExplorerPage.tsx`의 테스트는 `ExplorerPage.test.tsx`입니다.
6. **파일 이름**: 컴포넌트는 `PascalCase.tsx`(`ObjectCard.tsx`), 그 밖의 코드는 `camelCase.ts`(`handlers.ts`, `types.ts`)로 씁니다.
7. **가짜 응답은 `mocks/handlers.ts`에 모읍니다.** 개발 서버와 테스트가 같은 응답을 씁니다. 파일이 커지면 `mocks/handlers/<기능>.ts`로 나눕니다.
8. **API 호출은 기능 폴더의 `api.ts`에 모읍니다.** 화면 컴포넌트에서 `fetch`를 직접 쓰지 않고, `api/client.ts`를 거쳐 호출합니다. 가짜 응답과 타입은 [C106 API 관리 DB](https://app.notion.com/p/fb5c0ebaff7d446991d1c5adb0fdc5a8?v=405bdf14d2d881c58c39000c1d8d12b0)의 명세와 같은 모양으로 맞춥니다.

## API 클라이언트·공통 오류 (101)

기능별 `api.ts`에서 `src/api/client.ts`의 `apiGet`, `apiPost`, `apiPatch`, `apiDelete`를 사용합니다. 기본 경로는 `/api/v1`이고 세션 쿠키는 같은 출처 요청에 브라우저가 전달합니다. Authorization 헤더나 브라우저 저장소의 인증 토큰을 만들지 않습니다.

```typescript
import { ApiError, apiGet, apiPatch } from '../../api/client'

const result = await apiGet<MyData>('/명세에-정의된-경로')
// result.data, result.meta를 사용합니다.

try {
  await apiPatch('/명세에-정의된-경로', {/* API별 요청 필드 */})
} catch (error) {
  if (error instanceof ApiError) {
    // kind로 공통 처리하고 code로 도메인 오류를 구분합니다.
    // error.fieldErrors는 입력 폼에, error.requestId는 문의 시 추적에 사용합니다.
  }
}
```

- `apiGet`은 기존처럼 `{ data, meta? }`를 반환합니다. POST·PATCH·DELETE는 본문이 있으면 같은 응답을 반환하고, 204이면 `undefined`입니다. 204를 빈 JSON 객체로 위장하지 않습니다. 조회 GET은 명세상 data 응답이 필요하므로 204를 응답 형식 오류로 처리합니다.
- POST·PATCH·DELETE는 요청할 때마다 `XSRF-TOKEN` 쿠키를 읽어 URL 디코딩한 뒤 `X-XSRF-TOKEN` 헤더로 전달합니다. 로그인은 서버에서 CSRF 검사 예외이므로 쿠키가 없어도 요청할 수 있습니다. 다른 변경 요청에 쿠키가 없으면 서버가 검사·거절합니다. 토큰을 임의 생성하거나 CSRF 실패 요청을 자동 재전송하지 않습니다.
- 로그인 성공 시 서버가 CSRF 쿠키를 발급하며, 인증 상태 복원 시 `GET /auth/me`가 쿠키를 재발급할 수 있습니다. 이 인증 흐름 연결은 103에서 구현합니다.
- `ApiError`는 `Error`를 상속해 기존 화면의 `error.message` 사용과 호환됩니다. HTTP `status`, 서버 오류 `code`·`details`·`requestId`, 공통 분류 `kind`, 폼 오류 `fieldErrors`를 제공합니다. 오류 본문에 추적 ID가 없으면 `X-Request-Id` 응답 헤더를 확인합니다.
- `kind`는 401 `unauthenticated`, 403 `forbidden`, 400·422 `validation`, 409 `conflict`, 404 `not-found`, 5xx `server`입니다. 그 외 HTTP 오류는 `http`, 연결 실패는 `network`, 취소는 `aborted`, 성공 상태의 잘못된 JSON·공통 응답 구조는 `invalid-response`로 구분합니다. HTTP 응답이 없으면 status는 null이며 서버 오류 코드가 없으면 code는 null입니다.
- 서버의 오류 메시지를 우선 사용합니다. HTML·빈 본문·잘못된 오류 구조면 HTTP 상태별 기본 문구를 사용합니다. 로그인 실패·CSRF 거절·임시 비밀번호 등 API별 메시지를 공통 문구로 덮어쓰지 않습니다.
- 이 계층은 화면 이동·세션 상태 변경·토스트 표시를 직접 수행하지 않습니다. 103의 인증 상태 처리와 102·104의 화면·권한 안내에서 분류된 오류를 사용합니다. 403을 일괄 로그아웃으로 처리하지 않습니다.
- 마지막 인자의 `{ signal }`로 요청을 취소할 수 있습니다. 요청 함수 자체는 자동 재시도하지 않습니다. TanStack Query 등의 상위 계층 재시도 정책은 별도입니다. 변경 요청 실패 시 서버에서 이미 처리했을 가능성이 있으므로 무조건 다시 보내지 않습니다.
- 오류·요청 본문·쿠키·비밀번호를 콘솔이나 저장소에 남기지 않습니다. 이 변경은 API·DB 계약을 바꾸지 않습니다.

검사는 fetch를 가짜 응답으로 대체해 요청 헤더·메서드·응답·오류를 확인합니다. 실제 서버 세션·쿠키·CSRF 연동이나 브라우저 로그인 완료를 검증하는 검사는 아닙니다. Notion의 개별 API 001·099 페이지는 이번 연결에서 접근되지 않아 저장소 개발 가이드 8.3·11.1과 백엔드 AuthController·SecurityErrorResponder의 계약을 대조했습니다. 운영 Swagger와 `/v3/api-docs`에서도 기본 경로·data/meta 응답·로그인 200·로그아웃 및 비밀번호 변경 204를 확인했습니다. Swagger에는 세션·CSRF·공통 오류 문서가 충분하지 않고 `/auth/me`의 서버 주입 인자 `csrfToken`이 필수 query로 노출됩니다. 프론트에서는 이를 query로 만들지 않으며 백엔드 문서 보완이 필요합니다.

```bash
npm test -- --run src/api/client.test.ts
```

## 코드 모양 (Prettier)

코드 모양은 사람이 맞추지 않고 Prettier에 맡깁니다. 규칙은 `.prettierrc.json`에 있습니다.

| 규칙             | 값                                 | 예                                  |
| ---------------- | ---------------------------------- | ----------------------------------- |
| 한 줄 최대 길이  | 80자 (`printWidth`)                | 넘으면 여러 줄로 나눔               |
| 들여쓰기         | 공백 2칸 (`tabWidth`, `useTabs`)   |                                     |
| 세미콜론         | 쓰지 않음 (`semi`)                 | `const a = 1`                       |
| 문자열 따옴표    | 작은따옴표 (`singleQuote`)         | `'정상'`                            |
| JSX 속성 따옴표  | 큰따옴표 (`jsxSingleQuote`)        | `<input type="password" />`         |
| 객체 키 따옴표   | 꼭 필요할 때만 (`quoteProps`)      | `{ id: 'PR-03' }`                   |
| 끝 쉼표          | 여러 줄이면 항상 (`trailingComma`) | 마지막 항목 뒤에도 `,`              |
| 중괄호 안 공백   | 넣음 (`bracketSpacing`)            | `{ id }`                            |
| JSX 닫는 `>`     | 새 줄에 (`bracketSameLine`)        |                                     |
| 화살표 함수 괄호 | 항상 (`arrowParens`)               | `(item) => item.id`                 |
| 줄바꿈 문자      | 파일에 있던 것 유지 (`endOfLine`)  | Windows·Mac 차이로 생기는 경고 방지 |

- 저장 전에 `npm run format`을 실행하거나, VS Code의 Prettier 확장에서 저장 시 자동 정리를 켭니다.
- `public/mockServiceWorker.js`, `package-lock.json`은 도구가 만드는 파일이라 `.prettierignore`로 제외합니다.
- 모양에 관한 ESLint 규칙은 `eslint-config-prettier`로 꺼서 두 도구가 충돌하지 않게 합니다.

## 공통 UI (102)

- `components/Button.tsx`: 기본 버튼은 `type="button"`입니다. 폼 전송 시 `type="submit"`을 지정합니다. 요청 중에는 `pending`을 전달해 클릭을 막고 `aria-busy`로 알립니다. 실제 중복 실행 방지와 권한 검사는 서버 책임입니다.
- `components/DataTable.tsx`: `label`로 표 이름을 지정하고 기존 `thead`·`tbody`를 전달합니다. 좁은 화면에서 표 영역을 가로로 스크롤합니다.
- `components/StatusBadge.tsx`: 상태 문구와 `tone`을 전달합니다. 업무 상태 코드와 색상의 매핑은 해당 기능 화면이 결정하며 색상만으로 상태를 구분하지 않습니다.
- `components/Feedback.tsx`: `LoadingState`, `EmptyState`, `ErrorState`로 로딩·빈 결과·실패를 구분합니다. 실패 시 서버 안내·필드 오류·요청 ID를 표시하고 내부 상세 데이터는 펼쳐 출력하지 않습니다.
- `ErrorState`의 `onRetry`에는 조회 함수만 연결합니다. 401·403·입력 오류·409 상태 충돌에는 재시도 버튼이 없습니다. 로그인 이동·권한별 화면은 103·104에서 연결합니다.
- `components/Dialog.tsx`: 제목 연결, 모달 내부 탭 이동, Esc·배경·닫기 버튼으로 종료, 배경 스크롤 제한, 닫힌 뒤 호출 위치 포커스 복귀를 제공합니다. 한 번에 하나의 모달을 사용합니다.

실행 이력·정의 변경 이력·객체 연결 근거 화면에서 공통 표와 상태 표시를 재사용합니다. 기존 조회 조건과 API 계약은 유지합니다. 모달은 기존 연결 근거 화면에서 사용합니다.

검증 명령은 `npm test -- --run src/components/CommonUi.test.tsx`이며, 기존 화면 회귀 검증은 전체 테스트로 확인합니다. 102의 자동 테스트·브라우저 표시·피그마 디자인 대조는 변경 후 별도로 확인해야 합니다.

## 로그인·인증 (103)

- `/login`은 피그마의 서비스 소개·로그인 카드 구성을 기준으로 구현했습니다. 로고는 텍스트, 장식 이미지는 CSS로 구성했으며 원본 이미지와 세부 시각 대조는 별도 확인 대상입니다.
- 시작할 때 `GET /api/v1/auth/me`로 인증 상태를 복원합니다. 확인 전에는 업무 화면을 렌더링하지 않고, 401은 로그인으로 이동합니다. 연결 실패·서버 오류는 인증 만료로 처리하지 않고 조회 재시도를 제공합니다.
- 로그인은 `POST /api/v1/auth/login`에 `loginId`, `password`를 전달합니다. 성공 후 원래 요청한 내부 화면으로 이동하며, 서버 세션 쿠키·CSRF 처리는 101의 클라이언트를 사용합니다. 비밀번호·세션·CSRF 값을 브라우저 저장소에 보관하지 않습니다.
- 로그아웃은 `POST /api/v1/auth/logout`의 성공 또는 이미 만료된 401을 확인한 뒤 계정별 조회·변경 캐시를 비웁니다. 다른 오류는 로그아웃 성공으로 표시하지 않습니다.
- 보호 화면의 TanStack Query 조회·변경에서 발생한 401은 인증 상태를 만료시킵니다. 403은 세션을 유지하고 화면의 오류 안내로 표시합니다. 직접 API 클라이언트를 사용하는 변경 화면도 인증 실패를 처리해야 합니다.
- `mustChangePassword` 계정은 `/change-password`로 안내하며 API 003으로 변경 후 내 계정을 다시 조회합니다. 비밀번호 정책의 최종 검사는 서버가 담당합니다. 역할별 메뉴 제한은 104 범위입니다.
- 로컬 개발용 모의 로그인은 `demo-user` / `demo-only`만 허용합니다. 실제 계정이 아닌 고정된 테스트 데이터이며 모의 세션은 메모리에만 있어 새로고침 시 초기화됩니다. 모의 데이터에서는 실제 HttpOnly·Secure 쿠키나 서버 CSRF 검증을 확인할 수 없습니다. 모의 응답의 요청 로그는 비활성화했습니다.
- 테스트 설정은 기존 화면 회귀 검증을 위해 기본 모의 계정을 설정하고, 인증 전용 테스트에서는 익명·만료·오류 상태를 각각 지정합니다.

## 역할별 메뉴·화면 접근 (104)

- API 002의 `roleCode`·계정 상태·임시 비밀번호 여부를 기준으로 화면 접근을 판단합니다. 역할을 브라우저 저장소나 주소 파라미터로 선택하지 않습니다.
- `ADMIN`은 업무 메뉴와 관리자 메뉴를 사용할 수 있습니다. `PLANNER`·`MAINTENANCE`·`VIEWER`는 업무 데이터·AI 업무 도우미·실행 이력 메뉴를 사용하며 관리자 메뉴는 표시하지 않습니다. 실행 이력에서 실제로 조회 가능한 범위와 객체·속성별 조회 권한은 서버가 결정합니다.
- `/admin`과 그 하위 주소는 `RequireAccess`가 관리자로 제한합니다. 데이터 연결·연결 규칙·정의·규칙 이력·계정 관리의 메뉴와 직접 진입에 같은 기준을 적용합니다. 권한이 없는 화면은 자식 컴포넌트를 렌더링하지 않으므로 해당 관리 API도 요청하지 않습니다. 로그인 상태는 유지하며 권한 부족 안내를 표시합니다.
- 업무 화면도 등록된 네 역할의 활성 계정만 허용합니다. 모르는 역할·잠금·비활성 계정에는 화면 접근을 허용하지 않습니다. 임시 비밀번호 분기는 103의 변경 화면 안내가 우선합니다.
- `PermissionGate access="administration"`을 사용하면 관리 전용 버튼·링크도 같은 기준으로 표시할 수 있습니다. 이것은 화면 표시 도구이며 서버 권한 검사를 대신하지 않습니다. 아직 구현되지 않은 재배정·업무 실행 버튼의 세부 권한을 이 분류로 임의 확정하지 않습니다.
- 서버가 403으로 거부하면 102의 공통 오류 안내를 표시하고 로그아웃하지 않습니다. 새 API 002 응답에서 계정·역할·상태가 바뀌면 이전 범위의 조회·변경 캐시를 제거합니다. 서버에서 역할 변경으로 세션이 만료되면 기존 103의 401 처리로 로그인 화면에 이동합니다.
- 근거: 이 문서의 관리자 경로 구분, 개발 가이드 11.2, 백엔드 `DataSourceController`의 ADMIN 검사. Notion 기능 명세·최종 시나리오는 현재 연결에서 404로 접근하지 못했습니다. 세부 업무 권한 매트릭스는 확인 전이며, 이 작업은 기존 구현 화면과 공통 표시 도구 범위입니다.

로컬 개발 전용 모의 계정은 `demo-admin`(관리자), `demo-user`(생산기획), `demo-maintenance`(정비), `demo-viewer`(조회)이며 모의 비밀번호는 모두 `demo-only`입니다. 실제 서버 계정과 관계없으며 운영에서 사용할 수 없습니다.

- 로컬 모의 계정 발급은 목록·상세·변경 검사용입니다. 새로 발급한 모의 계정의 비밀번호 인증은 구현하지 않았으며, 역할별 로그인은 기존 `demo-admin`·`demo-viewer`를 사용합니다. 실제 계정 생성·첫 비밀번호 변경·Viewer 접근 차단은 서버에서 확인해야 합니다.
- 계약 근거는 최신 백엔드 AdminAccountController·AdminRoleController·DTO·AdminAccountService·PasswordPolicy입니다. Notion 명세·피그마 대조는 미완료이며 API·DB·서버 인증 정책 변경은 없습니다.
- `AccountsPage.test.tsx`에 생성·조회·변경·중복·충돌·권한·비밀번호 처리 테스트를 추가했습니다. 실행 결과는 아직 확인하지 않았습니다.

## 팀 결정이 필요한 항목

- 백엔드 개발 서버 주소·포트 (인증은 API 명세 001에 따라 세션 쿠키 + `X-XSRF-TOKEN` 헤더)

## 배포

- `develop`에 머지되면 Jenkins가 `frontend/` 변경을 감지해 `frontend/Dockerfile`로 이미지를 굽고 서버의 frontend 컨테이너를 교체합니다. 헬스체크를 통과하지 못하면 직전 버전으로 자동 롤백됩니다. 절차는 `infra/README.md`의 "자동 배포"를 참고합니다.
- 서비스 주소는 `https://k15c106.p.ssafy.io/` 이고, `/api/v1` 요청은 메인 nginx가 backend로 넘깁니다.
