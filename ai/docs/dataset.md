표 구성
- 기업 예시의 ERP·MES 표 29개와 표·컬럼이 같습니다. 수량은 `numeric(14,3)`, 출퇴근 시각은 `time`입니다.
- 담당 컬럼(구매 `buyer`, 검수 `inspector`, 영업 `sales_rep`, 정비 `technician`)에는 부서 코드가 아니라 부서 이름을 적었습니다.
- 더한 것: 표 4개(작업지시 공정별 배정 `work_order_operation`, 교대 메모 `handover_note`, 변경 이력 `erp.change_log`·`mes.change_log`), 컬럼 2개(수주 참조 `work_order.so_ref`, 최소 톤수 `routing.min_tonnage`)
- 값은 모두 새로 만들었습니다. 시드가 고정되어 있어 같은 명령이면 같은 파일이 나옵니다(`CHECKSUMS.sha256` 동일).
- 표 사이에 외래키 제약이 없어서 관계는 값으로만 확인할 수 있습니다.

데이터 규칙 (일부러 넣은 사례만 예외)
- 수주 → 작업지시 → 공정 배정 → 실적·불량·자재 투입 → 출하·검사 → 전표 순서로 서로 맞습니다.
- 수량·금액: 불량은 작업지시 = 실적 합 = 불량 기록 합, 출하·입고 수량은 상세 = 실제 합, 분개는 차변 = 대변, 재고는 흐름 계산과 같음
- 같은 설비의 실적은 겹치지 않고, 비가동 중에는 작업하지 않습니다. 실적 시간은 준비 시간 + 수량 × 표준 사이클 × 효율(8~30% 느림)입니다.
- 교대는 주간 08~17시, 야간 20~05시입니다. 실적이 있는 작업자는 그날 근태가 출근입니다.

## 4. 정답 파일

| 파일 | 내용 |
| --- | --- |
| `ontology.json` | 객체 유형 29(표마다 하나), 속성 214(모든 컬럼), 관계 57(컬럼 관계 53 + 메모 관계 4). 원천 정책의 금지 표·컬럼은 뺌(아래 "금지 데이터") |
| `mapping_rules.json` | 연결 규칙 5개: R-SO 수주 참조, R-W 작업자 → 직원, R-ITEM 품목, R-LOT 로트, R-ALIAS 메모 속 설비 이름 |
| `id_links.json` | 값 단위 정답 297건: `matched` 연결, `unmatched_error` 오류로 안 이어짐, `unmatched_expected` 원래 안 이어짐, `missing` 빈 값, `ambiguous` 후보 여럿 |
| `integrity_checks.json` | 정합성 검사 8건의 기대 판정 (K3 제외) |
| `integrity_issues.json` | 검사로 나와야 할 문제 10건(미연결 8, 조건 위반 2) |
| `note_annotations.json` | 메모·정비 기록 75건의 추출 정답: 위치(`start`·`end`), 부정·추정(`assertion`), 연결(`resolution`), 시각(`normalized`) |
| `scenario_answers.json` | 시나리오 질문의 기대 답 |
| `planted_cases.json`, `manifest.json` | 일부러 넣은 사례 목록, 버전·건수 |

읽는 법
- 연결 규칙의 변환은 `reference_transforms`에 출발(`source_transforms`)과 도착(`target_transforms`)을 따로 적습니다. AI 후보의 연결 규칙도 같은 형식이라 바로 비교할 수 있습니다. 예: R-W `[{"op": "PAD_ZEROS", "arg": 4}, {"op": "ADD_PREFIX", "arg": "GP"}]` → `[]`
- 위치는 `원천.표.컬럼`(예: `mes.work_order.so_ref`)으로 적습니다. `level: must`는 반드시 찾아야 하는 정답이고, 채점은 이름이 아니라 원천 위치로 합니다.
- 관계는 `via.from → via.to`이고, 두 컬럼 이상이면 목록입니다.
- 금지 데이터: 백엔드 `axcore.source-data-policy`(사본 `app/source_policy.py`)의 금지 표(`erp.attendance`·`erp.fixed_asset`·`erp.change_log`·`mes.change_log`)와 금지 컬럼(`erp.employee`의 `emp_name`·`position`·`hire_date`·`employment_type`·`status`, `mes.worker.name`)은 객체·속성·관계·규칙·사례 어디에도 넣지 않습니다. 이를 제안하지 않아도 감점되지 않고, 제안하면 정답에 없는 후보로 셉니다. 원천 데이터(`data-v1.0`)에는 원천 계정 허용 목록을 시험하려고 그대로 둡니다.
- `via.key`: 도착 컬럼이 기본키(`primary`), 다른 유일 키(`alternate`), 키 아님(`none`, 예: 라우팅 설비 종류 → 설비 종류)
- `via.condition`: 그 값일 때만 성립 (예: 정비 대상 종류 = 설비 / 금형)
- `via.through`: 다른 표를 거쳐 잇는 관계. 생산 실적·불량 기록·작업지시 공정별 배정의 작업지시 번호로 작업지시의 품목 코드를 찾고, 공정 순번과 함께 라우팅 한 줄을 가리킵니다.

값 단위 정답 `id_links.json` (출발 값 하나에 한 줄, 297줄)

```json
{"rule_id": "R-W", "from_value": "57", "to_value": null, "status": "unmatched_error", "reason": "직원 표에 GP0057 없음", "row_keys": ["57"]}
```

| status | 뜻 | 수 |
| --- | --- | --- |
| `matched` | 이어짐 | 288 |
| `unmatched_error` | 오류로 안 이어짐 (57 → GP0057 없음, 없는 수주 번호 등) | 6 |
| `unmatched_expected` | 원래 안 이어지는 값 (아직 검사 전인 로트) | 1 |
| `missing` | 출발 값 없음 | 1 |
| `ambiguous` | 후보 여럿 (메모의 "1호기" → P101·P201) | 1 |

- 항목(`from_value` 원본 값, `to_value` 대응 대상, `reason` 실패 이유, `row_keys` 그 값이 나오는 행)이 시험 적용 판정 근거 화면의 항목과 같습니다.
- `unmatched_error`·`ambiguous`인 값이 개별 보류 후보입니다. 연결률은 행 기준입니다(R-SO 136행 중 134행, 빈 값 3행 제외).

정답을 정하며 확인한 관계 3건

| 관계 | 확인 결과 |
| --- | --- |
| `routing.equipment_kind` → 설비 | 특정 설비가 아니라 설비 종류. 정답은 `equipment.kind` (키가 아니라 N:M) |
| `work_order.die_drawing_code` → 금형 | `die_code`가 아니라 `drawing_code`와 같은 값 |
| `inspection.lot_no` → 출하 | 출하 `lot_no`와 같은 값(161건). 검사 기록이 없는 출하 로트를 잡으려고 방향은 출하 → 검사 |

AI 입력에는 표 정의(표·컬럼·자료형·기본키), 컬럼 주석, 값만 씁니다. 관계는 AI가 찾아야 하는 대상이라 컬럼 주석에 다른 표 이름을 적지 않았습니다.
