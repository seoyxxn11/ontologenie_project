# 4. 시연 시나리오

프레스 공정 공장의 ERP·MES 원천 데이터(팀이 만든 합성 데이터, 기준 시각 2026-10-30 14:00)를 연결해, AI 제안으로 온톨로지를 만들고 Agent로 설비 고장에 대응하는 흐름입니다. 시나리오 번호는 [README](../README.md) 2절(S1~S7)과 같습니다.

## 4.0 시연 전 준비

| 항목 | 확인 |
| --- | --- |
| 서비스 주소 | `https://ontologenie.com` (Chrome 권장) |
| 계정 | 관리자 1개(ADMIN). 민감 값 열람을 보여 줄 때만 PLANNER 계정을 따로 만듭니다(계정·권한 화면). 비밀번호는 팀이 보관 |
| 원천 | ERP·MES 원천 서버가 켜져 있고, 데이터 연결 화면에서 `ERP_MAIN`·`MES_MAIN` 연결 확인이 성공 |
| 수집 | Kafka Connect 커넥터 2개가 RUNNING, batch의 CDC 소비자가 켜져 있음 |
| LLM | GMS 키가 유효하고 크레딧이 남아 있음(AI 분석·Agent 모두 사용) |
| 시연 데이터 | 원천이 `ai/data/data-v1.0` 상태. 전에 CDC 시연을 했다면 `ai/data/scenario-v1.0/cdc_99_restore.sql`로 되돌림. S5에서 쓸 `s5_fix.sql`은 아직 적용하지 않음 |

## 4.1 로그인 (S7)

| 순서 | 화면·경로 | 동작 | 보여 줄 것 |
| --- | --- | --- | --- |
| 1 | 로그인 `/login` | 관리자 계정으로 로그인 | 로그인 실패가 쌓이면 계정 잠금, 임시 비밀번호 계정은 첫 로그인 때 비밀번호 변경(`/change-password`) |
| 2 | 상단 메뉴 | 메뉴 확인 | 역할에 따라 메뉴가 다름. 관리자는 데이터 연결·연결 규칙·객체 유형·정합성 검사·계정·Action 정의까지 보임 |

## 4.2 원천 데이터 연결과 AI 분석 (S1)

| 순서 | 화면·경로 | 동작 | 보여 줄 것 |
| --- | --- | --- | --- |
| 1 | 데이터 연결 `/admin/sources` | ERP 원천 `ERP_MAIN` 선택 → 접속 정보 → **연결 확인** | 조회 전용 계정으로 접속 성공, 읽을 수 있는 표 목록. 원천에는 쓰지 않음 |
| 2 | 같은 화면, 원천 표본 | 표 하나(예: `erp.sales_order`)의 표본 보기 | 금지·민감 컬럼은 표본에서 빠짐(원천 데이터 정책) |
| 3 | 같은 화면, **분석 관리** | 분석 범위로 ERP·MES 표 선택 → **최초 분석** 실행 | 분석 작업 진행 상태. AI가 객체 유형·속성·관계·연결 규칙 후보를 근거·신뢰도와 함께 만듦 |
| 4 | 같은 화면 | 분석 완료 확인 | 후보 수, 비정형 자료(현장 메모·인계 메모)에서 뽑은 문서 연결 후보 |

## 4.3 제안 검토와 온톨로지 적용 (S2)

| 순서 | 화면·경로 | 동작 | 보여 줄 것 |
| --- | --- | --- | --- |
| 1 | 연결 규칙 `/admin/rules` | 분석 후보 목록에서 객체 유형 후보(예: 설비) 열기 | 제안 내용(속성·원천 매핑), **제안 근거**(원천 컬럼, 표본, 신뢰도) |
| 2 | 같은 화면 | 연결 규칙 후보 열기(예: MES 작업지시 ↔ ERP 수주) | 규칙 시험 적용 결과: 수주 참조 연결률 134/136(98.5%), 연결되지 않은 원천 키 |
| 3 | 같은 화면, **검토 결정** | 규칙 승인. 직원 매칭이 안 되는 일부 값(예: 57 → GP0057)은 보류 | 승인 즉시 정의·매핑 반영, 원천 다시 읽기 시작. 결정 이력 |
| 4 | 같은 화면, 규칙 후보 수정 | 관계·속성을 이름으로 검색해 조건을 고친 뒤 저장 | 새 개정으로 저장되고 다시 시험 적용 |
| 5 | 객체 유형 `/admin/object-types` | 유형 하나 열기 → 그룹(PRODUCTION) 지정 | 그룹이 없는 유형은 아무도 못 봄(조회 범위). 민감 속성은 민감 등급으로 표시 |
| 6 | 정의·규칙 이력 `/admin/history` | 방금 바꾼 정의 확인 | 누가 언제 무엇을 바꿨는지 전후 기록 |

## 4.4 정합성 문제와 재검증 (S5)

| 순서 | 화면·경로 | 동작 | 보여 줄 것 |
| --- | --- | --- | --- |

## 4.6 작업지시 재배정 계획 생성 (S4)

| 순서 | 화면·경로 | 동작 | 보여 줄 것 |
| --- | --- | --- | --- |
| 1 | AI 업무 도우미 `/agent` | "JB2610-0141을 P101이나 P201에서 이어서 생산할 수 있어? 각 설비의 능력을 비교해 줘." | 공정 20·30은 최소 400톤 필요. P101(400톤) 충족, P201(300톤) 미충족 |
| 2 | 같은 대화 | "JB2610-0141 남은 수량을 P101에서 찍으면 몇 시간?" | 3,200개 × 11.5초 ≈ 10.2시간(준비 70분 포함 11.4시간). 교대를 반영한 완료 예상 10-31 15:34, 납기 안 |
| 3 | 같은 대화 | "JB2610-0141을 P101로 옮기는 재배정 계획을 저장해 줘." | Agent가 재배정 계획 생성 Action을 부르고, 서버가 권한·설비 조건·작업지시 상태를 검증한 뒤 계획 저장. 답변 안 **실행 결과**에서 계획 펼치기(P103 → P101, 공정 20·30) |
| 4 | 같은 대화(선택) | "P201로 옮기는 계획도 저장해 줘." | 서버 검증에서 막힘(300톤 < 400톤). Agent가 막힌 이유를 그대로 전함 |
| 5 | 실행 이력 `/audit` | 방금 실행한 Action 열기 | 실행자, 입력, 결과, 바뀐 행 전후. 원천 MES의 배정은 바꾸지 않고 플랫폼 안에 계획만 저장 |

## 4.7 관리 기능 (S7, 공통)

| 순서 | 화면·경로 | 동작 | 보여 줄 것 |

## 4.8 시연 뒤 정리

- `s5_fix.sql`을 적용했다면 다음 시연 전에 원천 ERP를 `data-v1.0` 상태로 되돌립니다(`erp.item`의 BRK-990T와 `erp.change_log`의 71번 행 삭제, 또는 원천 재적재 후 다시 읽기).
- 시연 중 만든 재배정 계획과 대화는 플랫폼 DB에만 남고 원천에는 영향이 없습니다.
