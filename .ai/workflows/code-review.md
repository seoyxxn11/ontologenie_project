# Code Review Workflow

먼저 [AI 협업 규칙](../rules/ai-collaboration.md), [코드 규칙](../rules/code.md), [아키텍처 규칙](../rules/architecture.md), [테스트 규칙](../rules/testing.md)을 읽는다. API 변경이 있으면 [API 규칙](../rules/api.md)을, DB Schema·Entity·Migration·Repository·SQL 변경이 있으면 [DB 규칙](../rules/database.md)을, 인프라·배포 설정 변경이 있으면 [인프라 규칙](../rules/infra.md)을 함께 읽는다.

## Step 1. 변경 범위 분석

Base / Target Branch, 변경된 파일, Commit, 전체 Diff, 변경 목적을 확인한다. 비교 대상을 근거 없이 추측하지 않는다. 저장소가 없거나 비교 대상이 불명확하면 필요한 정보를 요청하고 확인 가능한 범위와 한계를 보고한다.

Branch 리뷰에서는 확인된 Target을 기준으로 `git log <target>..HEAD --oneline`, `git diff <target>...HEAD`를 사용할 수 있다. `<target>`은 실제 참조로 대체한다. 미커밋 변경 리뷰라면 `git diff`, `git diff --staged`와 관련 미추적 파일의 실제 내용을 확인한다. MR 리뷰라면 해당 MR의 Source/Target과 실제 Diff를 확인한다.

변경된 줄뿐 아니라 관련 호출부·계약·테스트를 읽는다. 전체 맥락 없이 일부 코드만으로 단정하지 않는다.

## Step 2. Correctness

해당 기술과 변경사항에 관련된 경우 다음을 우선 확인한다.

- 잘못된 조건문, null 또는 빈 값 처리
- 예외 처리 누락, 상태 변경 오류, 잘못된 데이터 처리
- 데이터 정합성, 동시성 문제, Transaction 문제

## Step 3. Architecture

아키텍처 규칙을 기준으로 책임 분리, 의존성 방향, 불필요한 결합, 중복된 책임, 기존 설계 원칙 위반을 확인한다. 프로젝트에서 확정하지 않은 아키텍처를 강요하지 않는다.

## Step 4. API

API 변경이 있을 때만 확인한다. 경로·응답·오류 형식이 API 규칙과 OpenAPI 명세에 맞는지, 요청·응답 필드나 상태 코드가 바뀌었는지, Entity를 직접 반환하는지 확인한다. 계약이 바뀌었는데 명세 수정이 없으면 보고한다.

## Step 5. Database

DB 관련 변경이 있을 때만 N+1, 불필요한 Query, Index, Transaction 범위, Lock 범위, 대량 데이터 처리를 확인한다. 이미 실행된 Migration 파일 수정, `rowVersion` 충돌 검사 누락, DB 제약 조건 없이 애플리케이션 검사에만 의존하는 중복 방지도 확인한다. 실제 근거 없는 성능 문제를 단정하지 않는다.

조회·저장 코드가 [DB 규칙](../rules/database.md)의 "조회·저장 방식"을 따르는지 확인한다. 새로 쓰거나 고친 코드(메서드 단위)만 본다. 기존 코드의 차이는 Minor 제안으로만 적는다.

- JPA(파생 쿼리, Specification, `@Query`, Entity가 있는 테이블의 native `@Query`·`@Modifying`)로 쓸 수 있는 조회·저장을 JdbcClient로 짰는가.
- JdbcClient를 썼다면 클래스나 메서드 주석에 허용 경우가 적혀 있는가. `repository` 패키지 밖에서 JdbcClient를 쓰는가.
- 이미 같은 일을 하는 JPA 메서드가 있는데 새 조회를 만들었는가.
- 요청 값을 SQL 문자열에 이어 붙였는가(보안 문제로 본다). 코드가 정한 값(클래스 상수, enum, 허용 목록에서 고른 컬럼 이름, 코드가 만든 파라미터 이름과 조건 조각)을 이어 붙인 것은 문제로 보지 않는다.
- 다른 도메인 테이블을 SQL로 바꾸는가. 한 번의 join·검사로 끝나지 않는 조회를 다른 도메인 테이블에 직접 하는가.
- 같은 트랜잭션에서 Entity가 있는 테이블을 JdbcClient로 바꾸는가. 섞었다면 SQL 전 flush와, 뒤에 같은 Entity를 읽을 때 `clear`·`refresh`가 있는가.
- 새 SQL을 실제로 실행하는 통합 테스트가 있는가.

## Step 6. Security

보안에 관련된 변경과 영향을 확인한다. 인증, 인가, 입력 검증, Injection, 민감정보 노출, 권한 우회 가능성을 점검한다. 권한 검사가 서버에 있는지, 비밀값이나 토큰이 코드·로그에 들어가는지 확인한다.

## Step 7. Infra

`infra/`, `Jenkinsfile`, `Dockerfile`, compose 파일, nginx 설정 변경이 있을 때만 확인한다. 인프라 규칙을 기준으로 포트가 `127.0.0.1`에만 열리는지, 이미지 버전이 고정되었는지, 비밀값이 파일에 직접 들어갔는지, 데이터 볼륨을 지우는 명령이 있는지, 헬스체크가 있는지 확인한다. `Jenkinsfile` 변경은 서버에서 실행될 명령과 그 영향을 확인한다.

## Step 8. Testing

변경사항을 검증하는 테스트 존재 여부, 정상 경로, 실패 경로, 경계값, 기존 동작 영향, 필요한 회귀 테스트를 확인한다. 실행 가능한 환경과 권한이 있으면 관련 테스트를 실행한다. 실행한 명령·결과와 실행하지 못한 검증을 구분한다.

## Step 9. Convention

코드 규칙과 확정된 프로젝트 컨벤션을 적용한다. Formatter나 Linter가 검출할 수 있는 단순 스타일 문제는 우선순위를 낮춘다.

## Step 10. Review Output

| Severity | 기준 | 처리 |
| --- | --- | --- |
| Critical | 데이터 손실, 심각한 보안 문제, 서비스 중단 가능성, 치명적인 정합성 문제 | 반드시 수정 대상으로 보고 |
| Major | 실제 버그 가능성이 높은 문제, 중요한 설계 규칙 위반, 검증이 필요한 주요 결함 | 수정 또는 명시적인 검토 필요 |
| Minor | 유지보수성·가독성 개선, 성능 최적화 제안 | 개선 제안으로 구분 |

문제는 Critical, Major, Minor 순서로 보고한다. 각 항목에는 다음을 포함한다.

- Severity
- 파일 및 코드 위치: 확인한 경로와 줄 번호, 줄 번호를 확인할 수 없으면 심볼 등 실제 위치 정보
- 문제 내용
- 실제 문제가 발생할 수 있는 구체적인 조건과 근거
- 수정 방향

문제를 억지로 만들어내지 않는다. 실제 코드로 뒷받침할 수 있는 문제를 우선하고, 추측을 확정적인 문제로 표현하지 않는다. 단순 취향 차이를 오류처럼 지적하지 않는다.

발견한 문제가 없으면 그렇게 보고하되, 확인한 범위와 검증 한계를 함께 명시한다. 검토하지 못한 범위까지 안전하다고 보증하지 않는다. 실제 실행한 검증과 미해결 질문도 보고한다.

리뷰 요청만으로 코드를 수정하거나 원격 리뷰 댓글을 게시하지 않는다. 자동 리뷰가 통과했다고 사람이 승인한 것으로 처리하지 않는다.
