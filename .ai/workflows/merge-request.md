# Merge Request Workflow

먼저 [AI 협업 규칙](../rules/ai-collaboration.md), [Git 규칙](../rules/git.md), [Code Review Workflow](code-review.md)를 읽는다. 테스트를 실행한다면 [테스트 규칙](../rules/testing.md)도 읽는다. 코드 리뷰를 수행하는 에이전트는 Code Review Workflow가 지정한 규칙 문서를 모두 읽는다.

## 실행 순서

1. Git 저장소 여부와 현재 Branch를 확인한다. 저장소가 없으면 초기화하지 않고 실행 불가 이유를 보고한다. 작업 트리의 미커밋 변경도 확인해 MR에 포함되는 변경과 구분한다.
2. Target Branch와 원격 저장소를 확인한다. 사용자 요청과 프로젝트의 확정된 설정을 우선한다. [Git 규칙](../rules/git.md)에 따라 작업 Branch의 기본 Target은 `develop`이다. `hotfix/*`처럼 Target이 정해지지 않은 Branch는 추측하지 않고 확인을 요청한다. 로컬 원격 추적 정보의 최신 여부를 확인할 수 없으면 그 한계를 표시한다.
3. 확인된 Target 참조와 현재 Branch의 Commit 차이를 확인한다. `git log <target>..HEAD --oneline`으로 대상에 없는 Commit을 확인한다. `<target>`은 실제 확인한 참조로 대체하며 명령 예시를 그대로 실행하지 않는다.
4. `git diff <target>...HEAD`로 공통 조상 이후 현재 Branch의 전체 Diff를 읽고 변경 파일·추가·삭제·이름 변경을 확인한다. 참조나 공통 조상을 확인할 수 없으면 원인을 보고하고 비교를 완료했다고 표현하지 않는다.
5. 아래 [코드 리뷰](#코드-리뷰) 절차를 수행한다. MR 본문 초안만 요청받은 경우에도 수행한다.
6. 변경 목적과 기존 기능에 미치는 영향을 파악한다.
7. 주요 변경사항을 정리한다.
8. 중요한 구현 선택과 그 이유를 정리한다.
9. 실제 수행한 검증 내용과 결과를 정리한다. 기록의 출처를 구분하고 실행하지 않은 테스트를 수행했다고 작성하지 않는다.
10. 테스트하지 못한 부분과 기능 영향 확인이 필요한 부분을 표시한다.
11. 리뷰어가 집중해서 볼 부분을 정리한다. 아래 [MR 본문 기재](#mr-본문-기재) 기준에 따라 코드 리뷰 요약을 함께 정리한다.
12. 프로젝트 루트의 `.gitlab/merge_request_templates/Default.md`를 실제로 읽고 본문 초안에 적용한다. 제목은 Git 규칙의 MR 제목 형식을 따른다. Jira 이슈 키는 사용자 요청, Branch 이름, Commit에서 확인한다. 이슈 번호만 확인되면 `S15P31C106-` 접두사를 붙여 전체 키로 쓴다. 이슈 여부를 확인할 수 없으면 추측하지 않고 확인을 요청한다. 체크리스트는 확인된 항목만 체크한다.
13. 원격 MR 생성 또는 수정은 해당 작업에 대한 사용자의 명시적 요청이 있을 때만 실행한다. 코드 리뷰 결과에 Critical 또는 Major 항목이 있으면 이 Workflow 안의 Push와 원격 작업 전에 멈추고 [리뷰 결과 처리](#리뷰-결과-처리) 기준을 따른다. 저장소, Source/Target Branch, 제목·본문, 기존 MR 유무를 확인하고 이용 가능한 GitLab 도구로 수행한다. 새 MR이 필요한지 기존 MR 수정인지 구분한다. 원격 Branch가 없으면 필요한 Push를 별도 권한 기준에 따라 처리하며 자동으로 승인된 것으로 보지 않는다.

## 코드 리뷰

4단계에서 확인한 Target 참조와 Diff 범위를 기준으로 [Code Review Workflow](code-review.md)를 수행한다. 4단계 Diff는 Commit된 변경만 포함한다. 1단계에서 MR에 포함할 미커밋 변경을 확인했다면 그 변경도 리뷰 범위에 넣는다. MR에 포함하지 않을 미커밋 변경은 리뷰 범위에서 뺀다.

### 리뷰 수행 주체

변경을 작성한 세션이 자기 코드를 직접 리뷰하지 않는다. 도구가 서브에이전트(별도 컨텍스트에서 실행되는 하위 에이전트)를 지원하면 리뷰를 서브에이전트에 맡긴다.

서브에이전트에는 다음만 전달한다.

- 프로젝트 루트 경로, 현재 Branch, 확인된 Target 참조
- 리뷰 범위: `<target>...HEAD` Diff와 포함할 미커밋 변경 여부
- 변경 목적: 사용자 요청이나 Jira 이슈처럼 출처를 확인한 내용만
- 읽어야 할 문서: Code Review Workflow와 그 문서가 지정한 규칙
- 작업 제약: 읽기 전용으로 리뷰하며 코드 수정, Commit, Push, 원격 작업을 하지 않는다

작성자의 구현 의도 해석, 이미 검증했다는 판단, 문제가 없다는 결론은 전달하지 않는다.

서브에이전트를 사용할 수 없으면 현재 세션에서 리뷰한다. 이 경우 작성 세션이 직접 리뷰했다는 사실을 결과에 표시한다.

### 리뷰 결과 처리

작성 세션은 리뷰 결과를 삭제하거나 Severity를 낮추지 않는다. 동의하지 않는 항목은 결과를 그대로 둔 채 근거를 따로 적는다. 리뷰 결과는 MR 초안과 함께 보고한다. 리뷰 결과만을 이유로 코드를 수정하지 않는다. 사람의 지시로 지적 항목을 수정했다면 바뀐 Diff로 리뷰를 다시 수행한다.

Critical 또는 Major 항목이 있으면 이 Workflow 안의 Push와 원격 MR 생성·수정 전에 멈춘다. 해당 항목을 보고하고 진행 여부를 사람에게 확인받는다. 원격 MR 생성 요청을 이미 받았더라도 이 확인을 생략하지 않는다.

### MR 본문 기재

코드 리뷰 요약을 MR Template의 `리뷰 요청사항` 절에 작성한다. 요약에는 다음을 포함한다.

- 리뷰 수행 주체: 서브에이전트 또는 작성 세션
- Severity별 항목 수
- Critical·Major 항목: 파일 위치, 한 줄 문제 요약, 처리 상태(수정 후 재리뷰 완료, 사람 확인 후 진행, 미해결(사람 확인 대기), 작성자 이견과 근거)
- 발견 항목이 없으면 그 사실과 확인 범위·검증 한계
- AI 리뷰 결과이며 사람의 리뷰와 승인을 대신하지 않는다는 표시

Minor 항목은 수만 적거나 짧게 나열한다. 리뷰 전문은 MR 본문에 옮기지 않고 사용자에게 보고한다. 원격 리뷰 댓글은 게시하지 않는다.

## 작성 원칙

MR은 단순 변경 파일 목록이 아니다. 왜 변경했는지, 무엇이 달라졌는지, 중요한 구현 선택, 검증 방법, 리뷰어가 확인할 부분을 설명한다. 특별한 판단이 없는 단순 변경의 구현 설명은 간결하게 작성한다.

## 결과 보고와 작업 경계

MR 본문 초안 작성과 실제 원격 생성·수정을 구분한다. 코드 리뷰 결과와 리뷰 수행 주체(서브에이전트 또는 작성 세션)를 함께 보고한다. 원격 작업을 수행했다면 도구 결과를 확인하고 MR 링크와 Source/Target Branch를 보고한다. 도구·인증·권한이 없거나 실행에 실패하면 작성한 초안과 구체적인 제한을 제공한다. MR 생성 후 자동으로 Merge하지 않는다.
