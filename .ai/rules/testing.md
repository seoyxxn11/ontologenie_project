# 테스트 규칙

팀 가이드 원본은 [C106 개발 가이드](../../docs/development-guide.md) 12절이다.

## 기본 원칙

- 변경사항과 관련된 테스트를 우선 확인한다.
- 테스트가 없으면 필요한 테스트를 제안하거나 작성한다.
- 버그 수정 시 가능하면 재현 테스트를 작성한다.
- 중요한 실패 경로를 검증한다.
- 기존 테스트를 통과시키기 위해 검증을 약화하지 않는다.
- 테스트를 임의로 삭제하거나 Skip하지 않는다.
- 실행하지 않은 테스트를 성공했다고 말하지 않는다.
- 테스트가 실패하면 실패 원인과 영향을 보고한다. 원인을 확인하지 못했으면 미확인으로 표시한다.

명령어는 프로젝트의 문서와 실제 설정에서 확인한다. 테스트 도구나 환경이 없으면 실행 불가 이유와 필요한 검증을 보고한다. 테스트 실행의 권한도 [AI 협업 규칙](ai-collaboration.md)을 따른다.

## 테스트 종류

| 테스트 | 목적 | 도구 |
| --- | --- | --- |
| 단위 테스트 | Service·Handler 규칙 검증 | JUnit, Mockito |
| API 테스트 | 요청·응답·오류 확인 | Spring MVC Test |
| DB 통합 테스트 | 실제 SQL·제약·트랜잭션 확인 | Testcontainers |
| AI 테스트 | 분석·추출 결과 검증 | pytest |
| 프론트엔드 테스트 | 화면 상태·사용자 동작 확인 | Vitest 등 |
| E2E 테스트 | 전체 시나리오 확인 | 통합 시나리오 테스트 |

## 실행 명령

| 서비스 | 명령 | 비고 |
| --- | --- | --- |
| 백엔드 | `backend/`에서 `./gradlew build` | 테스트와 포맷 검사(`spotlessCheck`)를 함께 실행한다. Testcontainers를 쓰므로 Docker가 실행 중이어야 한다. |

## 필수 테스트 범위

핵심 기능은 다음 경우를 확인한다.

- 정상 처리
- 필수 입력 누락
- 잘못된 입력값
- 존재하지 않는 대상
- 권한이 없는 사용자
- 중복 요청
- 상태 충돌
- 트랜잭션 실패 후 데이터 상태

Coverage 수치 기준은 두지 않는다. 위 필수 범위와 개발 가이드 12.3의 C106 핵심 테스트로 충분성을 판단한다.

## C106 핵심 테스트

- 온톨로지·승인: 검사를 통과하지 않은 후보는 승인할 수 없다. 검사 후 revision이 바뀌면 재검사가 필요하다. 승인과 반영은 함께 성공하거나 함께 실패한다. 규칙 개정 후 유효하지 않은 기존 연결은 비활성화된다.
- 수집·배치: 최초 수집은 전체 적재, 다음 수집은 변경분만 반영한다. 반복 수집해도 같은 객체의 ID가 유지된다. 동시 수집 요청은 하나의 실행으로 처리한다. 실패한 작업이 체크포인트를 전진시키지 않는다.
- Action·재배정: 권한이 없으면 실행할 수 없다. 같은 요청 ID가 계획을 중복 생성하지 않는다. 작업지시·공정 중복을 거절한다. 계획 생성은 원천 MES를 변경하지 않는다. 차단된 실행도 감사 기록에 남긴다.
- 정합성 문제: 같은 열린 문제가 중복 생성되지 않는다. 재검증을 통과하지 않으면 해결 상태가 될 수 없다. 재검증은 변경된 데이터를 기준으로 한다.

## Team Decision Needed

현재 검사 구성과 결정 대기 항목은 [249 협의안](../../docs/ci-quality-criteria-249.md)에 정리한다. 협의안은 미확정 초안이며 새 필수 범위나 임계값을 규칙으로 적용하지 않는다. 팀 합의 후 개발 가이드·이 문서·Notion 사본을 함께 갱신한다.

다음 항목은 아직 미결정이다. 임의로 정하지 않는다.

- CI 필수 테스트 범위
- AI·프론트엔드 실제 테스트 명령 (서비스 골격 구성 시 기록)
- Test Naming Convention
- 동시성 및 성능 테스트 기준
