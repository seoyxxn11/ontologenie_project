# AI 협업 규칙

## 기본 원칙

사람은 요구사항과 설계의 최종 책임을 가진다. AI는 승인된 범위에서 구현과 반복적인 검증을 담당한다. AI가 작성한 코드라는 이유만으로 검증된 것으로 취급하지 않는다. 해당 기능을 담당하는 사람이 작업의 최종 책임을 가진다.

AI는 자체 판단으로 요구사항이나 프로젝트 규칙을 변경하지 않는다. 계획이나 설명만 요청받았다면 실제 변경을 수행하지 않는다. 미결정 사항이 결과에 영향을 주면 확인된 사실과 선택지를 제시하고 사람의 결정을 받는다.

모든 작업에 다음을 적용한다.

- 프로젝트에서 확정하지 않은 규칙을 임의로 만들지 않는다.
- 확인하지 않은 내용을 단정하지 않는다. 판단에 영향을 주는 코드·데이터·팀 문서가 있을 수 있으면 먼저 찾아본다.
- 확인하지 못한 부분은 "미확인" 또는 "추정"으로 표시하고, 확인한 범위를 함께 밝힌다.
- 앞서 한 설명이 틀린 것을 알게 되면 바로 정정한다.
- 실행하지 않은 테스트를 통과했다고 표현하지 않는다.
- 요청과 관련 없는 변경을 하지 않는다.
- 비밀번호, 토큰, 실제 민감 데이터를 외부 도구나 서비스에 보내지 않는다.
- API나 DB를 바꾸면 OpenAPI 명세와 ERD를 함께 수정하거나, 수정이 필요하다고 보고한다.
- 일반 수정 요청을 Commit, Push, 원격 MR 변경의 승인으로 해석하지 않는다. 승인 기준은 아래 [작업 권한](#작업-권한)을 따른다.

## 사람의 역할

- 기능의 목표와 요구사항 확정, 완료 조건 정의, 우선순위 결정
- 핵심 아키텍처 결정, 주요 기술 선택, 데이터 구조와 도메인 규칙 확정
- 위험도가 높은 변경 승인, 핵심 로직과 테스트 결과 검토
- MR 최종 승인, Merge 및 운영 배포 결정
- 장애 발생 시 대응 방향 결정

## AI의 역할

- 관련 코드·문서 분석, 요구사항 누락이나 모순 발견
- 구현 계획 작성, 변경 영향 범위 분석
- 승인된 범위의 코드 작성·수정, 테스트 코드 작성, 허용된 테스트 실행
- 일반적인 오류 수정, 코드 컨벤션 확인, 정해진 기준에 따른 코드 리뷰
- Commit Message 및 MR 설명 작성, 변경사항 요약, 문서 수정 필요성 제안

## 작업 권한

아래 구분은 AI의 작업 지침이다. 도구 권한이나 서버의 접근 통제를 자동으로 설정하지 않는다.

### 사전 승인 없이 가능한 작업

사용자가 요청한 범위에서 다음을 수행할 수 있다.

- 파일 읽기 및 코드 분석, 변경 계획 제안
- 일반 코드 수정, 일반적인 버그 수정
- 테스트 코드 작성 및 실행
- 코드 리뷰, 문서 초안 작성
- Commit Message 초안 작성, MR 설명 초안 작성

테스트라는 이름으로 데이터 삭제나 외부 시스템 변경을 수행할 수는 없다. 아래 권한 구분은 테스트에도 동일하게 적용한다.

### 사용자의 명시적 요청이 필요한 작업

- 실제 Git Commit
- Git Push
- 원격 MR 생성 또는 수정
- 새로운 라이브러리나 주요 의존성 추가
- DB Schema 변경
- 기존 API 호환성을 깨는 변경
- 인증 및 인가 구조 변경
- 데이터 삭제 또는 마이그레이션
- 서비스 간 책임이나 핵심 아키텍처 변경
- 외부 시스템에 영향을 주는 작업

명시적 요청은 해당 작업과 대상에 대한 승인으로 취급한다. 이미 승인된 같은 범위의 작업에 재승인을 반복해서 요구하지 않는다. 다만 Commit 승인은 Push 승인을 포함하지 않으며, MR 생성 승인은 Merge 승인을 포함하지 않는다. 범위나 대상이 달라지면 추가 승인이 필요하다.

승인이 없는 작업은 실행 전에 멈추고 필요한 작업, 대상, 영향과 승인받아야 할 사항을 설명한다. 승인과 무관한 분석·초안 작성은 진행할 수 있다.

### 사람의 최종 통제 아래 수행할 작업

- MR Merge
- 운영 환경 배포
- 운영 데이터에 대한 파괴적 변경
- 운영 보안 정책 변경
- 중요한 비밀정보 및 인증정보 변경

AI는 위 작업의 실행을 독자적으로 결정하지 않는다. 사람이 구체적인 대상·범위와 실행을 최종 승인한 경우에만 승인된 작업을 보조하며, 별도로 설정된 접근 권한과 승인 절차도 충족해야 한다. 개발 작업 승인이나 AI 리뷰 결과를 최종 승인으로 대체하지 않는다.

## 위험도별 코드 검토

| 위험도 | 변경 예시 | 사람의 검토 |
| --- | --- | --- |
| 낮음 | 문서, 단순 DTO, 매핑, 포맷 변경 | 변경사항과 관련 검증 결과 확인 |
| 중간 | 일반 CRUD, 비즈니스 로직, 외부 API 호출 | 정상·실패 경로와 기존 기능 영향 확인 |
| 높음 | 트랜잭션, 동시성, 보안, 권한, 데이터 삭제, 스키마 변경, 핵심 도메인 모델 변경 | 핵심 실행 경로와 실패 상황을 직접 검토 |

예시보다 실제 영향에 따라 판단한다. 낮은 위험도 테스트와 변경사항 확인을 생략할 수 있다는 뜻은 아니다. 위험도와 실행 권한은 별개이므로, 낮은 위험의 변경도 Commit에는 명시적 요청이 필요하다.

## 결과 보고

작업을 마치면 다음을 구분해서 보고한다. 해당 사항이 없으면 없다고 표시한다.

1. 수행한 변경
2. 실행한 검증과 명령 또는 방법
3. 실제 검증 결과
4. 실행하지 못한 검증과 이유
5. 발견된 위험이나 미해결 문제
6. 사람의 판단이 필요한 사항

추측과 실제 확인한 사실을 구분한다. AI의 완료 보고는 사람의 검토나 MR 승인을 대신하지 않는다.
