# 아키텍처 규칙

팀 가이드 원본은 [C106 개발 가이드](../../docs/development-guide.md) 6·7.2·10절이다.

## 기본 원칙

- 이미 확정된 프로젝트 구조와 책임 경계를 존중한다.
- 아키텍처 변경이 필요하면 먼저 변경 이유를 설명한다. 실행 권한은 [AI 협업 규칙](ai-collaboration.md)을 따른다.
- 기존 외부 계약의 호환성을 고려한다.
- 여러 모듈에 영향을 주는 변경은 영향 범위를 분석한다.
- 팀에서 정하지 않은 아키텍처를 절대 규칙처럼 적용하지 않는다.

## 저장소 구조

모노레포 안에서 서비스별 코드를 분리한다. 권장 구조는 `backend/`, `ai/`, `frontend/`, `infra/`, `docs/`, `.gitlab/`, `Jenkinsfile`이다. 실제 저장소의 기존 폴더 이름을 우선한다. 구조 변경은 팀과 협의한다.

## 백엔드 패키지

도메인 중심으로 구성한다. 루트 패키지는 `com.axcore.platform`이다. 확정 기술 스택은 개발 가이드 6.2를 따른다.

- 같은 프로세스를 여러 개 띄워도 맞게 동작해야 한다. 작업·잠금·카운터 같은 상태를 인스턴스 메모리에만 두지 않는다.
- 실행 모드는 프로필로 나눈다: `api`(웹 서버), `batch`(배치 컨테이너), `local`(로컬 개발).

- 도메인: `auth`, `account`, `ontology`, `source`, `mapping`, `analysis`, `review`, `check`, `issue`, `batch`, `action`, `agent`, `audit`
- 공통: `global` (`config`, `error`, `security`, `response`, `entity`)
- 도메인 안은 필요한 계층만 둔다: `controller`, `dto`, `service`, `domain`, `repository`, `handler`

`global`에는 여러 도메인이 실제로 쓰는 코드만 둔다. 기능과 관계없는 범용 코드를 넣지 않는다.

## 계층별 책임

| 계층 | 책임 |
| --- | --- |
| Controller | HTTP 요청·응답 처리, 입력값 검사 시작 |
| Service | 업무 흐름과 트랜잭션 |
| Repository | 데이터 저장·조회 |
| Handler | Action의 검증과 실행 |
| DTO | API 요청·응답 데이터 |

- Entity를 API 응답으로 직접 반환하지 않는다.
- 도메인 간 데이터 변경은 해당 도메인의 Service를 통해 처리한다.
- 단순 Entity 조회만 하는 Service를 불필요하게 분리하지 않는다.

## Transaction

- 읽기 전용 조회는 `@Transactional(readOnly = true)`를 쓴다.
- 하나의 업무에서 함께 성공해야 하는 DB 변경은 하나의 트랜잭션으로 처리한다.
- 외부 AI 호출이나 원천 DB 조회를 오래 걸리는 DB 트랜잭션 안에서 실행하지 않는다.

## 서비스 연동

- Spring Boot가 주요 업무 데이터 저장과 권한 검사를 맡는다.
- FastAPI는 분석·제안 결과만 반환한다. 플랫폼 업무 DB에 직접 쓰지 않는다.
- 서비스 사이의 요청·응답 DTO를 따로 정의한다.
- AI 호출에는 시간 제한을 둔다. 호출 실패와 분석 실패를 구분하고, 실패한 호출은 호출 식별자와 원인을 기록한다.
- 모델 출력은 서버에서 검증한 후 저장한다. AI가 만든 객체 유형이나 연결 규칙은 검토·승인 전에 활성 데이터로 반영하지 않는다.
- ERP/MES 원천 DB에는 조회 전용 계정(플랫폼)과 CDC 복제 계정(Debezium)으로만 접속한다. 원천에 쓰지 않고, 변경 이력 테이블·트리거도 만들지 않는다. 자격 증명을 API 응답이나 로그에 넣지 않는다.
- 원천 수집은 로그 기반 CDC(Debezium → Kafka → 배치 소비자)로 한다. 매핑된 테이블의 첫 적재와 매핑 변경 뒤 다시 읽기는 전체 읽기로 하고, 체크포인트(소비 offset)는 객체 반영과 같은 트랜잭션에서만 옮긴다. 자세한 규칙은 개발 가이드 10.2다.
- Kafka는 원천 CDC에만 쓴다. 서비스 사이 작업 전달은 실행 기록 테이블로 한다.

## 배치

- CDC 반영은 배치 컨테이너의 상시 소비자가 한다. 같은 테이블의 전체 다시 읽기를 중복 실행하지 않는다. 이미 실행 중이면 기존 실행 ID를 반환한다.
- 시작·완료·실패 시각을 기록하고 실행 중에는 heartbeat를 갱신한다. heartbeat가 멈춘 작업은 시간 초과 기준으로 실패 처리한다.
- 수동 실행과 예약 실행은 같은 수집 로직을 쓴다.
- 반복 실행해도 같은 원천 데이터가 중복 생성되지 않게 한다.
- `@Scheduled`와 작업 실행은 batch 프로필에서만 돈다. api는 작업 표에 `QUEUED` 행을 넣기만 한다.
- 배치 작업은 작업 종류마다 `batch.service.QueuedJobHandler`를 구현한다. 가져오기·실패 처리·감사 결과 줄은 `QueuedJobRunner`가 맡는다. 첫 적재처럼 큰 작업은 Handler 안에서 Spring Batch Job으로 실행한다. 자세한 내용은 [C106 개발 가이드](../../docs/development-guide.md) 10.3이다.
